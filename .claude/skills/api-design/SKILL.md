# API 設計 Skill

---

## 目的

- API Gateway + Lambda で公開する小さな API を一貫して設計する
- ZAP / CodeQL の検査対象として安定した形にする
- 低コスト（呼び出し回数・レイテンシ・運用負荷）を維持する

## 使用するタイミング

- 新しいエンドポイントを追加するとき
- 既存エンドポイントの I/O を変更するとき
- API レスポンスのフォーマットを統一したいとき
- ZAP やセキュリティ検査の前提を整えたいとき

## 手順

### 1. 用途と読み手を確定する

- だれが叩く API か（フロントエンド / バッチ / 外部）
- 読み取り中心か、状態変更があるか
- どのくらいの頻度で叩かれるか
- ZAP 検査対象に含めるか

### 2. URL とメソッドを決める

- リソース名は複数形・kebab-case
- 動詞は使わない（`GET /popular-posts` は OK、`/getPopularPosts` は NG）
- 学習目的のためでも、最小本数で十分（最初は 1〜2 本）

例:

```txt
GET /popular-posts        # 人気記事ランキングを返す
GET /popular-posts/:slug  # 特定記事のランキング情報（必要なら）
```

### 3. 入力を厳格に定義する

- クエリ・パス・ボディ・ヘッダの全項目に型と制約を持たせる
- `zod` などで schema 化し、型は `z.infer` で導出する
- 想定外パラメータは無視ではなく拒否する（401/400 系で明示）

### 4. レスポンスを統一する

成功時:

```json
{ "data": { ... } }
```

リスト系:

```json
{
  "data": [ ... ],
  "meta": { "total": 12 }
}
```

エラー時:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed"
  }
}
```

ステータスコードは HTTP セマンティクスに従う（200 で全部返さない）。

### 5. ステータスコードを意識する

| コード | 用途                                 |
| ------ | ------------------------------------ |
| 200    | 取得成功                             |
| 304    | キャッシュ有効                       |
| 400    | リクエスト不正（JSON 不正等）        |
| 401    | 認証必要                             |
| 403    | 権限不足                             |
| 404    | リソース不在                         |
| 422    | 値が意味的に不正                     |
| 429    | レート制限超過                       |
| 500    | 想定外の内部エラー（詳細は出さない） |

### 6. ZAP 検査しやすい形にする

- 同一パスでメソッド差を増やしすぎない
- 認証ヘッダ・トークンの位置を統一する
- 「想定エラー応答」がきれいに返ることを保証する
- 内部エラー時にスタックトレース・SQL を返さない

### 7. キャッシュとコスト

- 静的に近いデータ（ランキング JSON）は CloudFront / API Gateway キャッシュを検討
- ただしキャッシュ導入はコスト・整合性影響を ADR で評価する
- レスポンスサイズを意識する（過剰なフィールドを返さない）

### 8. 仕様書化（任意）

- 規模が小さいうちは `apps/api/<feature>/<feature>Schema.ts` の
  zod スキーマを正本として扱う
- 必要があれば OpenAPI を後付けする（`zod-to-openapi` 等）。先回りして
  OpenAPI 駆動にしない（YAGNI）

## チェックリスト

エンドポイント追加・変更時に確認する。

- [ ] URL は名詞・複数形・kebab-case か
- [ ] メソッドが HTTP セマンティクスに合っているか
- [ ] 全入力に schema 検証があるか（`unknown` で受けて narrow しているか）
- [ ] レスポンスフォーマットが既存と統一されているか
- [ ] 想定エラーすべてにコードとメッセージが定義されているか
- [ ] エラー応答に内部詳細（スタック・SQL・PII）が漏れていないか
- [ ] ZAP 検査対象に追加すべきか判断したか
- [ ] レイテンシ・呼び出し回数の観点でコスト影響を評価したか
- [ ] テスト（正常系・異常系・境界値）が追加されているか
- [ ] CDK 側で IAM 権限が最小化されているか

## 禁止事項

- 200 で `success: false` を返して使い分ける
- エラー応答にスタックトレースや内部 ID を含める
- 認証なしで状態変更系エンドポイントを公開する
- ワイルドカード IAM で Lambda を動かす
- 仕様化されていない隠しパラメータ（debug=true 等）を残す
