# Sprint 作業計画 Skill

`documentation-coauthor` が Sprint 作業計画を作成するとき、このスキルをテンプレートとして使う。
orchestrator の Phase 2 でこのスキルを呼び出すこと。

---

## 設計書と作業計画の使い分け

| 種別 | 配置先 | 寿命 | 内容 |
|---|---|---|---|
| 設計書 | `docs/design/` | 長い | 判断・合意の記録。実装詳細は書かない |
| 作業計画 | `docs/sprints/<最新スプリント>/<PBI名>.md` | 短い | 実装 SubAgent への指示書。詳細を書く |

---

## 作業計画の必須セクション

### 1. 前提・依存関係

- この実装が完了している必要があるもの（他 PBI・マイグレーション・スキーマ等）
- ローカル環境の前提（Docker 起動・環境変数など）

### 2. 実装仕様

各機能の「変更前 / 変更後」対照表を機能ごとに作る。
SubAgent が迷わず実装できる粒度で書く。

```markdown
### <機能名>（サブタスク N）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 関数名 | handler | xxxHandler |
| ルーティング | 独立 Lambda | POST /api/xxx |
```

### 3. 削除対象ファイル（該当する場合）

削除するファイル・フォルダと削除理由を列挙する。
全削除前に `grep` で参照が 0 件であることを確認するコマンドを記載する。

### 4. ドキュメント更新

変更に伴って更新が必要な設計書・openapi.yaml・README などを列挙する。

### 5. 変更ファイル一覧

| 操作 | ファイルパス | 内容 |
|---|---|---|
| 新規 / 更新 / 削除 | `apps/api/src/...` | 変更の概要 |

### 6. SubAgent 割り当て表

```markdown
| # | サブタスク | SubAgent | 依存 |
|---|---|---|---|
| 1 | xxx | tdd-implementer | なし |
| 2 | yyy | tdd-implementer | #1 |
| N | テストリファクタリング | backend-engineer または test-engineer | 全実装サブタスク完了後 |
```

## テストレビューとリファクタリング（必須サブタスク）

中規模以上の実装（ハンドラー 3 本以上 / テストファイル 3 件以上）では、
全実装サブタスク完了後に必ずテストコードのリファクタリングサブタスクを設ける。

### 確認観点

1. **セットアップの重複**: 同じ `beforeAll` / `beforeEach` パターンが 3 ファイル以上に繰り返されていないか
2. **ヘルパー関数の重複**: `makeMockEvent` のような共通ヘルパーが各ファイルに個別定義されていないか
3. **テスト意図の可読性**: セットアップが肥大化してテストケースの意図が読み取れなくなっていないか

### 抽出の判断基準

- 同一のボイラープレートが 3 ファイル以上に存在する → 共通ヘルパーに抽出する
- 抽出後も「このテストは何をテストするか」が各ファイル内で読める状態を保つ（DAMP 原則: Descriptive And Meaningful Phrases）

### 実装パターン（参照実装）

このプロジェクトの参照実装: `apps/api/src/shared/test-helpers/mediumTestSetup.ts`

```typescript
// ヘルパー（shared/test-helpers/）に集約するもの
// - コンテナ起動・マイグレーション・共通シード
export function useTenantTestContainer(permissions: ...) {
  const ctx = { serviceDb: null, tenantDb: null };
  beforeAll(async () => { /* ... */ }, 120000);
  afterAll(async () => { /* ... */ });
  return ctx;
}

// 各テストファイルに残すもの（DAMP のため）
// - vi.mock（Vitest のホイスティング制約で移動不可）
// - テスト固有の権限設定（useTenantTestContainer の引数として渡す）
// - テーブルリセット（beforeEach）
// - テストケース本体
```

### 作業計画への記載方法

SubAgent 割り当て表の最後の行に追加する:

```markdown
| N | テストリファクタリング（セットアップ重複の共通ヘルパー抽出） | backend-engineer | 全実装サブタスク完了後 |
```

完了条件チェックリストに追加する:

```markdown
- [ ] テスト重複レビューを実施し、3 ファイル以上の共通ボイラープレートは共通ヘルパーに抽出されていること
- [ ] テストリファクタリング後も `npm run test` が全件 Green で通ること
```

## 完了条件チェックリストの末尾への必須追加

作業計画の完了条件チェックリストには、以下の 2 項目を**必ず最終行に追加**すること。
削除・順序変更は禁止。

```markdown
- [ ] `docs/pbi/README.md` の該当 PBI を `✅ 完了` に更新すること
- [ ] ユーザーの承認を得てから完了とすること
```

> 理由: コンテキスト圧縮が発生してもチェックリストはファイルとして残る。
> ワークフローの終了義務をチェックリストに書き落とすことで、文脈が失われても見落としを防ぐ。

## 設計書（`docs/design/` 配下）に書く内容

設計書は実装詳細を書かない。判断・合意の記録に限る。

含める内容:
- Phase 1 で検討した背景・選択肢・採用しなかった案の理由
- 外部から見える仕様（URI / API / データフロー / エラー方針 / スコープ等）
- 権限・認可・バリデーション方針
- テスト観点

禁止: ファイルパス・関数名・コンポーネント名などの実装詳細
（詳細は `.claude/skills/doc-coauthoring/SKILL.md` を参照）
