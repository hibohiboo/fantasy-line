# フロントエンド指針

このファイルは `apps/frontend` 配下のフロントエンド実装で常時守るべきルールを扱う。
詳細パターンは `.claude/skills/frontend-patterns/SKILL.md` を参照する。

---

## 1. SSR 前提

- 本体は SSR の SPA で配信する

## 2. 機能別配置

- `apps/frontend/src/features/` 配下に機能単位で実装をまとめる
- 例: `articles/`, `tags/`, `archive/`, `popular-posts/`
- UI コンポーネントとデータ取得・型・schema を同じ機能フォルダに置く
- 機能をまたぐ純粋ユーティリティは `apps/frontend/src/shared/` に置くが、
  「便利な置き場」にしない（複数機能から本当に使われるかを確認）

## 3. UI とデータ取得の混在を避ける

- ページコンポーネントは取得結果の表示と高水準のレイアウトに集中させる
- データ取得・整形は機能フォルダ内の関数（`fetchPopularPosts.ts` 等）に分離する
- API レスポンスは `zod` で検証してから UI に渡す（信頼境界）

## 4. アクセシビリティ

- 主要操作はキーボードでも完結するよう実装する
- 画像には意味のある `alt`、装飾画像には空の `alt=""` を付ける
- 見出し階層（`h1`〜`h6`）を飛ばさない
- フォーカス可視を消さない（CSS リセットで `outline: none` を残さない）
- カラーコントラストを WCAG AA を目安にする
- ARIA は HTML 標準で表現できない場合の最後の手段として使う

## 5. 表示の安全性

- 信頼できない HTML を生で挿入しない
- 外部リンクには `rel="noopener noreferrer"` を付与する
- 画像の遅延読み込みを既定にする（`loading="lazy"`）

## 6. パフォーマンス

- 重いコンポーネント（チャート、リッチエディタ等）は `lazy` + `Suspense` で遅延読み込み
- リストが長くなる箇所は仮想化を検討する
- 画像は `<picture>` 等を活用し、サイズを指定する

## 7. VRT 対象を増やしすぎない

- 全記事ページの VRT は行わない（コスト・時間・メンテ性）
- 代表ページに限定する
- VRT 対象を増やす場合は ADR で背景・運用負荷を明示する

## 8. SEO / OGP

- 内部リンクは相対パスを基本にする（移転耐性）

## 9. 状態管理

- グローバルストアは「本当に複数機能をまたぐ」場合のみ導入する
- 多くは親コンポーネントで十分
- Context は描画頻度の高い値に対して使わない（パフォーマンス影響）

## 10. やってはいけないこと

- 全ページ VRT 化
- 1 機能のために `shared/` を肥大化させる
- 入力サニタイズなしのユーザー入力 HTML 表示
- 意味のない ARIA 属性追加

---

## 11. 推奨フォルダ構成（`apps/frontend`）

- `src/features/<機能>/` に UI、データ取得、型、schema をまとめる
- `src/shared/ui/` にはサイト共通の UI（ヘッダー、フッター、SEO 等）
- `src/shared/lib/` には機能横断の純粋関数（`formatDate`, `slug` 等）
- `tests/` は Vitest 用、`playwright/` は E2E / VRT 用
- 機能専用コンポーネントを `shared/ui/` に置かない
