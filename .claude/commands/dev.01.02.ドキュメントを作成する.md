PBIドキュメントをもとに設計ドキュメントを作成します。

# タスク

1. PBIドキュメントを読み込み、機能の目的・スコープ・受け入れ条件を把握する
2. 関連する既存コード・設計を調査する
3. 以下の手順で設計ドキュメントを作成・更新する

---

# ドキュメント構成

設計ドキュメントは **基本設計・詳細設計・OpenAPI仕様・非機能要件** の4種に分けて管理する。
既存ファイルがある場合は更新し、新規の場合は作成する。

## 1. 基本設計 — `docs/design/basic/`

ファイル名: `docs/design/basic/<PBI番号>-<機能名>.md`

**記載内容:**
- **目的と背景**: この機能が必要な理由・解決する課題
- **対象読者**: PO・開発者・レビュアー
- **機能概要**: ユーザーストーリーをもとにした機能の全体像
- **システム構成**: 変更対象のコンポーネント・レイヤーの概要図
- **主要なユースケースフロー**: メイン・代替・例外フローの概要（詳細は詳細設計へ）
- **API一覧**: 新規・変更するエンドポイントの一覧と OpenAPI仕様へのリンク
  - 例: `GET /users/{id}` → [openapi.yaml#/paths/~1users~1{id}](../openapi/openapi.yaml)
- **データモデル概要**: 主要なエンティティの関係（ER図 or テーブル一覧）
- **制約・前提条件**: 依存するサービス・外部システム・環境

## 2. 詳細設計 — `docs/design/detail/`

ファイル名: `docs/design/detail/<PBI番号>-<機能名>.md`

**記載内容:**
- **対象読者**: 実装担当の開発者
- **処理フロー詳細**: シーケンス図（Mermaid形式）
- **API詳細**: 各エンドポイントのバリデーション・エラーハンドリング・レスポンス仕様（OpenAPI仕様へのリンクを併記）
- **データモデル詳細**: テーブル定義・インデックス・制約・マイグレーション方針
- **フロントエンドコンポーネント設計**: コンポーネント構成・Props・イベント（該当する場合）
- **エラーハンドリング方針**: 各異常系の処理とユーザーへの通知方法
- **実装上の注意点**: パフォーマンス・排他制御・トランザクション境界など

## 3. OpenAPI仕様 — `docs/design/openapi/`

ファイル名: `docs/design/openapi/openapi.yaml`（プロジェクト共通の単一ファイルで管理）

- **新規・変更エンドポイントを追記・更新する**
- OpenAPI 3.1 形式で記述する
- `tags` でPBI番号・機能名を付与して変更箇所を追跡可能にする
- 基本設計・詳細設計からこのファイルの該当パスへリンクを張る

```yaml
# 記述例
paths:
  /users/{id}:
    get:
      tags: [PBI-001, user]
      summary: ユーザー取得
      ...
```

## 4. 非機能要件 — `docs/design/non-functional/`

**横断的に影響する関心事（セキュリティ・ログ・エラー・パフォーマンスなど）は機能設計書に混在させず、このディレクトリに独立したドキュメントとして管理する。**

| ファイル名 | 内容 |
|---|---|
| `security.md` | 認証・認可方針、入力バリデーション、秘密情報の扱い |
| `logging.md` | ログレベル定義、出力フォーマット、個人情報マスク方針 |
| `error-handling.md` | HTTPステータスコード規約、エラーレスポンス形式、リトライ方針 |
| `performance.md` | レスポンスタイム目標、N+1対策方針、キャッシュ戦略 |

- 既存ファイルがある場合はPBIによる変更・追加点のみ差分更新する
- 基本設計・詳細設計から関連する非機能要件ドキュメントへリンクを張る

# ドキュメント品質チェック

設計ドキュメントを作成・更新した後、以下の6観点でセルフチェックを行い、NGの項目は修正すること。

## 観点1: 目的が明確か
- [ ] 何のための文書か冒頭に書かれているか
- [ ] 読者がこの文書を読んだ後に何ができるようになるか書かれているか
- [ ] スコープ・対象読者・重要なポイントが冒頭に書かれているか

## 観点2: 読者が明確か
- [ ] 対象のドキュメントを見て何をしたい読者向けか明記されているか
- [ ] 読者の前提知識（ツール・役割・スキル）が想定されているか

## 観点3: 構成が分かりやすいか
- [ ] 見出しだけで文書の流れがわかるか
- [ ] 背景・前提・手順・判断条件・注意点が混在していないか
- [ ] 必要な情報にすぐたどり着ける順番になっているか

## 観点4: 表現が具体的か
- [ ] 「適切に」「必要に応じて」「確認する」などのあいまいな表現が放置されていないか
- [ ] 主語が明確で、何を・誰が・いつ・どの条件で行うのかわかるか
- [ ] 用語が文書内で一貫しているか
- [ ] 文末表現（だ・である調）が統一されているか

## 観点5: 手順・判断条件が実行可能か
- [ ] 手順が番号付きで順番に書かれているか
- [ ] 判断が必要な箇所に条件が書かれているか
- [ ] 完了条件・例外時の対応が書かれているか

## 観点6: 保守しやすいか
- [ ] 管理者・問い合わせ先・関連資料がわかるか
- [ ] 最終更新日と更新が必要なタイミングが書かれているか
- [ ] 一時的な情報と恒久的な情報が混ざっていないか

---

# 完了条件

- 以下のドキュメントが作成・更新されていること
  - `docs/design/basic/<PBI番号>-<機能名>.md`（基本設計）
  - `docs/design/detail/<PBI番号>-<機能名>.md`（詳細設計）
  - `docs/design/openapi/openapi.yaml`（APIが変更される場合）
  - `docs/design/non-functional/` 配下の該当ファイル（横断的変更がある場合）
- 基本設計・詳細設計から OpenAPI仕様・非機能要件ドキュメントへのリンクが張られていること
- PBIの受け入れ条件を満たす設計になっていること
- ドキュメント品質チェックの全項目がOKであること
- 完了後は「設計ドキュメント作成完了」とチャットに書き込むこと
