PBIドキュメントをもとに設計ドキュメントを作成します。

# タスク

1. PBIドキュメントを読み込み、機能の目的・スコープ・受け入れ条件を把握する
2. 関連する既存コード・設計を調査する
3. 以下の手順で設計ドキュメントを作成・更新する

---

# ドキュメント構成と命名規則

設計ドキュメントは **基本設計・詳細設計・データモデル・OpenAPI仕様・非機能要件・実装ノート** に分けて管理する。

## 命名の原則

| ドキュメント種別 | 単位 | 命名規則 |
|---|---|---|
| 基本設計 | **対象（画面・ドメイン）** | `docs/design/basic/<対象名>.md` |
| 詳細設計 | **対象（画面・ドメイン）** | `docs/design/detail/<対象名>.md` |
| データモデル | **対象（ドメイン）** | `docs/design/data-model/<対象名>.md` |
| OpenAPI仕様 | プロジェクト全体 | `docs/design/openapi/openapi.yaml` |
| 非機能要件 | 横断関心事ごと | `docs/design/non-functional/<関心事名>.md` |
| 実装ノート | **PBIごと** | `docs/sprints/<sprint名>/<PBI番号>.md` |

**設計ドキュメントはPBI番号をファイル名に含めない。** 一つの画面や API は複数の PBI にまたがって更新されるため、対象の名前（画面名・リソース名・ドメイン名）をファイル名とする。どの PBI が変更したかはドキュメント内の変更履歴セクションで追跡する。

### 対象名の決め方

- 画面を対象とする場合: `user-profile`、`dashboard`、`item-list` など
- APIリソースを対象とする場合: `api-user`、`api-item`、`api-auth` など
- ドメイン横断の場合: `auth`、`notification`、`payment` など

既存ファイルがある場合は更新し、新規の場合は作成する。

## 1. 基本設計 — `docs/design/basic/<対象名>.md`

**対象読者: PO・開発者・レビュアー**

**記載内容:**
- **目的と背景**: この設計が必要な理由・解決する課題
- **対象読者**: PO・開発者・レビュアー
- **機能概要**: 対象画面・ドメインの全体像
- **システム構成**: レイヤー間の関係を概念レベルで示す図（Browser → API → DB 程度の粒度）
  - ファイルパスや具体的なクラス名は書かない（詳細設計へ）
  - 参照リンク: 「実装レベルの影響コンポーネント一覧は詳細設計の冒頭を参照」と記載する
- **主要なユースケースフロー**: メイン・代替・例外フローの概要（詳細は詳細設計へ）
- **API一覧**: 関連するエンドポイントの一覧と OpenAPI仕様へのリンク
  - 例: `GET /users/{id}` → [openapi.yaml](../openapi/openapi.yaml)
- **データモデル概要**: エンティティの関係を1〜3行の概念説明のみ記載し、詳細はデータモデルドキュメントへのリンクを張る
  - テーブル定義・カラム定義・インデックスは基本設計に書かない
- **制約・前提条件**: 依存するサービス・外部システム・環境
- **変更履歴**: どの PBI がいつ何を変更したかの記録

```markdown
## 変更履歴
| PBI | 変更内容 | 日付 |
|-----|---------|------|
| PBI-001 | 初版作成 | 2026-05-04 |
| PBI-012 | ○○機能追加 | 2026-06-01 |
```

## 2. 詳細設計 — `docs/design/detail/<対象名>.md`

**対象読者: 実装担当の開発者**

**記載内容:**
- **対象読者**: 実装担当の開発者
- **実装影響コンポーネント一覧**: 冒頭に必ず置く。変更対象のファイルパスと変更種別（新規/追加/変更）をテーブルで列挙する
- **処理フロー詳細**: シーケンス図（Mermaid形式）
- **API詳細**: 各エンドポイントのバリデーション・エラーハンドリング・レスポンス仕様（OpenAPI仕様へのリンクを併記）
- **データモデル詳細**: テーブル定義・インデックス・制約の詳細はデータモデルドキュメントへのリンクを張る。マイグレーション方針も同様
- **フロントエンドコンポーネント設計**: コンポーネント構成・Props・イベント（該当する場合）
- **エラーハンドリング方針**: 各異常系の処理とユーザーへの通知方法
- **実装上の注意点**: パフォーマンス・排他制御・トランザクション境界など
- **変更履歴**: 基本設計と同様の形式で記録

## 3. データモデル — `docs/design/data-model/<対象名>.md`

**対象読者: 開発者・レビュアー（DB設計の影響範囲を確認したい人）**

**記載内容:**
- **ER図**: エンティティ間の関係（テキスト図またはMermaid）
- **テーブル定義**: カラム名・型・制約・説明のテーブル
- **設計方針**: ユニーク制約の有無・型選択の理由など
- **CRUD表**: ユースケース（API エンドポイント）× テーブルの操作マトリクス（C/R/U/D）
- **変更履歴**: どの PBI がいつ何を変更したかの記録

**書かないもの（禁止事項）:**
- ORM スキーマのコードスニペット（コードが正本。実装起点スニペットは実装ノートへ）
- マイグレーション方針（プロジェクト共通規約のため非機能要件ドキュメントへ）

既存ファイルがある場合は更新し、新規テーブルが追加されたら CRUD表に行を追加する。

## 4. OpenAPI仕様 — `docs/design/openapi/openapi.yaml`

プロジェクト共通の単一ファイルで管理する。

- 新規・変更エンドポイントを追記・更新する
- OpenAPI 3.1 形式で記述する
- `x-pbi` 拡張フィールドで最終更新PBIを記録し、変更箇所を追跡可能にする
- 基本設計・詳細設計からこのファイルの該当パスへリンクを張る

```yaml
# 記述例
paths:
  /users/{id}:
    get:
      tags: [user]
      x-pbi: PBI-012
      summary: ユーザー取得
      ...
```

## 5. 非機能要件 — `docs/design/non-functional/`

横断的に影響する関心事（セキュリティ・ログ・エラー・パフォーマンス・マイグレーションなど）は機能設計書に混在させず、このディレクトリに独立したドキュメントとして管理する。

| ファイル名 | 内容 |
|---|---|
| `security.md` | 認証・認可方針、入力バリデーション、秘密情報の扱い |
| `logging.md` | ログレベル定義、出力フォーマット、個人情報マスク方針 |
| `error-handling.md` | HTTPステータスコード規約、エラーレスポンス形式、リトライ方針 |
| `performance.md` | レスポンスタイム目標、N+1対策方針、キャッシュ戦略 |
| `migration.md` | DBマイグレーションツール・命名規則・実行手順・禁止事項 |
| `logging.md` | ログの必須フィールド（userId・対象リソースID）・レベル定義・出力タイミング・禁止情報 |

- 既存ファイルがある場合はPBIによる変更・追加点のみ差分更新する
- 基本設計・詳細設計から関連する非機能要件ドキュメントへリンクを張る

## 6. 実装ノート — `docs/sprints/<sprint名>/<PBI番号>.md`

PBI固有の「実装開始時点のスナップショット」を記録する。設計ドキュメントとは役割が異なる。

**書くもの:**
- ORM スキーマのコードスニペット（実装の起点として。実装後はコードが正本となるため更新不要）
- PBI固有のマイグレーション手順（連番確認など、汎用方針ではない手順）
- 認証モックなど、この PBI 期間中だけ有効な暫定設計・制約

**書かないもの:**
- 基本設計・詳細設計・データモデルに書けば済む内容（重複禁止）
- 完了後も恒久的に参照される内容（適切な設計ドキュメントへ移動する）

# フロントエンドコンポーネントを設計する場合

PBIにUI変更が含まれる場合は、以下を必ず参照すること。

1. `docs/design/style-guide.md` — カラーパレット・Vuetify テーマ設定・コンポーネントパターン・命名規則の正本
2. `.claude/skills/frontend-design/SKILL.md` — 高品質なUIを生成するためのガイドライン

**Vuetify 使用上の原則:**
- Vuetify に存在するコンポーネントは必ず使用する（自作しない）
- テーマカラー外の色のハードコード禁止。`color="primary"` 等の Vuetify カラー名を使用する
- スタイルガイドに定義されていないコンポーネントパターンが必要な場合は、`style-guide.md` を先に更新してから実装する

# ドキュメント品質チェック

設計ドキュメントを作成・更新した後、以下の6観点でセルフチェックを行い、NGの項目は修正すること。

## 観点1: 目的が明確か
- [ ] 何のための文書か冒頭に書かれているか
- [ ] 読者がこの文書を読んだ後に何ができるようになるか書かれているか
- [ ] スコープ・対象読者・重要なポイントが冒頭に書かれているか

## 観点2: 読者が明確か
- [ ] 対象のドキュメントを見て何をしたい読者向けか明記されているか
- [ ] 読者の前提知識（ツール・役割・スキル）が想定されているか

## 観点3: 構成が分かりやすいか
- [ ] 見出しだけで文書の流れがわかるか
- [ ] 背景・前提・手順・判断条件・注意点が混在していないか
- [ ] 必要な情報にすぐたどり着ける順番になっているか

## 観点4: 表現が具体的か
- [ ] 「適切に」「必要に応じて」「確認する」などのあいまいな表現が放置されていないか
- [ ] 主語が明確で、何を・誰が・いつ・どの条件で行うのかわかるか
- [ ] 用語が文書内で一貫しているか
- [ ] 文末表現（だ・である調）が統一されているか

## 観点5: 手順・判断条件が実行可能か
- [ ] 手順が番号付きで順番に書かれているか
- [ ] 判断が必要な箇所に条件が書かれているか
- [ ] 完了条件・例外時の対応が書かれているか

## 観点6: 保守しやすいか
- [ ] 管理者・問い合わせ先・関連資料がわかるか
- [ ] 最終更新日と更新が必要なタイミングが書かれているか
- [ ] 一時的な情報と恒久的な情報が混ざっていないか

# 完了条件

- 以下のドキュメントが作成・更新されていること
  - `docs/design/basic/<対象名>.md`（基本設計）
  - `docs/design/detail/<対象名>.md`（詳細設計）
  - `docs/design/data-model/<対象名>.md`（DBを変更する場合）
  - `docs/design/openapi/openapi.yaml`（APIが変更される場合）
  - `docs/design/non-functional/migration.md`（DBを新規追加・変更する場合。初回は新規作成）
  - `docs/design/non-functional/` 配下の該当ファイル（その他横断的変更がある場合）
  - `docs/sprints/<sprint名>/<PBI番号>.md`（PBI固有の実装起点スニペット・暫定手順がある場合）
- 各設計ドキュメントの変更履歴セクションに今回のPBI番号・変更内容・日付が記録されていること
- 基本設計・詳細設計から OpenAPI仕様・データモデル・非機能要件ドキュメントへのリンクが張られていること
- 基本設計に実装レベルのファイルパスが混入していないこと（詳細設計の冒頭に置くこと）
- データモデルドキュメントに ORM スキーマのコードが含まれていないこと
- PBIの受け入れ条件を満たす設計になっていること
- ドキュメント品質チェックの全項目がOKであること
- 完了後は「設計ドキュメント作成完了」とチャットに書き込むこと
