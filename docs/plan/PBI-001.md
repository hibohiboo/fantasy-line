## 実装方針

- TDD（Red → Green → Refactor）の順序で実装する
- 依存関係の順序: スキーマ → DBスキーマ → マイグレーション → APIハンドラー → フロントエンド
- 認証は X-User-Id ヘッダーによるモック認証（PBI-014 未実装のため）
- 1チェックリスト項目 = 1コミットを目安にする
- **テスト方針**: テストは責務が生まれたレイヤーで1回だけ行う。上位レイヤーで下位レイヤーのロジックを再テストしない（詳細: [testing.md](../design/non-functional/testing.md)）
- **TDD の Red フェーズ**: "ファイルが存在しない" ことで失敗させるのは不適切。必ずスタブハンドラー（固定値を返す最小実装）を先に作成し、「振る舞いが間違い」で失敗させること
- **レスポンスのスキーマ検証**: テストでレスポンスボディをパースする際は `CreateVillageResponseSchema.parse()` / `ListVillagesResponseSchema.parse()` を使う。フィールドを個別にアサートするだけでなくスキーマ全体でパースすることで、フロントエンドとのスキーマ差異を型レベルで防ぐ（`echo.small.test.ts` の EchoResponseSchema パターン参照）

## 認証モック方針

- `X-User-Id` リクエストヘッダーの値を `owner_id` として使用する
- ヘッダーが存在しない場合は 401 Unauthorized を返す
- テストでは `headers: { 'X-User-Id': 'user-123' }` を設定して動作確認する
