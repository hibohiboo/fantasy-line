## 実装方針

- TDD（Red → Green → Refactor）の順序で実装する
- 依存関係の順序: スキーマ → DBスキーマ → マイグレーション → APIハンドラー → インフラ → フロントエンド → E2E
- 認証は X-User-Id ヘッダーによるモック認証（PBI-014 未実装のため）
- 1チェックリスト項目 = 1コミットを目安にする
- **テスト方針**: テストは責務が生まれたレイヤーで1回だけ行う（詳細: [testing.md](../design/non-functional/testing.md)）
  - Zod スキーマで全バリデーションルールをテストする → ハンドラーでは代表1ケースのみ
- **TDD の Red フェーズ**: ファイル不在でのエラーでなく、スタブ（固定値返却）を先に作り「振る舞いの失敗」で Red にすること
- **レスポンスのスキーマ検証**: テストでは `XXXResponseSchema.parse(JSON.parse(result.body))` でスキーマ全体をパースしてからアサートする
- **DB**: 既存コードは MySQL (mysql2 / drizzle-orm/mysql2) を使用しているため、resident テーブルも同じ MySQL ベースで実装する。`mysqlTable` / `serial` / `varchar` / `bigint` / `date` / `timestamp` を使用すること

## 実装上の注意点

### DB の型について（重要）

設計ドキュメント（resident.md）では PostgreSQL（`pgTable`, `bigserial`）の SQL 定義が記載されているが、
**既存コードは MySQL（`mysqlTable`, `mysql2`, Aurora MySQL Serverless V2）を使用している**。
実装時は `mysqlTable` と MySQL 互換の型を使用すること。

- `id`: `serial` (AUTO_INCREMENT + PRIMARY KEY)
- `villageId`: `bigint('village_id', { mode: 'number' })`
- `birthDate`: `date('birth_date', { mode: 'string' })` で "YYYY-MM-DD" 文字列として扱う
- `createdAt`: `timestamp('created_at').notNull().defaultNow()`

### カタカナバリデーション

読みのカタカナチェックは正規表現 `/^[ァ-ヴー]+$/` で行う。
フロントエンドのバリデーションも `CreateResidentSchema.shape.nameKana.safeParse()` を使いスキーマ駆動で行う。

### 権限チェックの順序

`createResident` および `listVillageResidents` ハンドラーでは以下の順序で処理する。
1. 認証チェック（401）
2. バリデーション（400）
3. 村の存在・所有権チェック（403）— 存在しない村と他ユーザーの村をまとめて 403

### レスポンスのスキーマ分離

`createdAt` は DB（Drizzle）からは `Date` オブジェクトで返るが、JSON.stringify 後は ISO 8601 文字列になる。
テストでは `ResidentResponseSchema`（`createdAt: z.string()`）を使ってパースすること。

### Testcontainers のテスト削除順

Medium テストの `beforeEach` では必ず `residents` テーブルを先に delete してから `villages` テーブルを delete すること（villages 参照の村削除で resident のデータが残るリスクを避ける）。
