## 方針

- このPBIのゴールは「戦略書を書くための計画」を確定させることであり、戦略の内容そのものを確定させることではない
- 論点ごとに Phase を分け、各 Phase の完了条件を「決定事項がドキュメント化されたこと」とする
- 既存の `testing.md`（実装ルール）と重複させない。戦略書は「なぜそのルールなのか」「どこまで適用するか」を扱い、実装の具体的ルールは現状の `testing.md` に残す
- 各 Phase はユーザー（プロジェクト所有者）の確認を経て確定する。書籍が指摘する「テンプレート穴埋め計画」（無難で効力のない記述、空虚な一文で済ませる）のアンチパターンを避ける
- Part VI（テストを支える技術）は読書メモ未着手のため、本計画では Part I〜V の内容のみを対象とする。読了後に論点が追加される可能性がある

---

## 論点と進め方（チェックリスト）

### Phase 1: テストレベル・テストタイプの整理

- [ ] 現状の `apps/api`・`apps/frontend` で実施しているテストレベル（Small/Medium/Large）をテストレベル/テストタイプの観点で棚卸しする
- [ ] 書籍の「テストレベル」「テストタイプ」の定義（Part I）と対応付け、欠けているテストタイプ（性能・セキュリティ・ロングラン等）がこのプロジェクトに必要か検討する
- [ ] 完了条件: 棚卸し結果の対応表を戦略書ドラフトに記載できる状態にする

### Phase 2: リスクベースのテスト戦略インプット整理

- [ ] プロジェクトリスクを列挙する（個人開発で割けるレビュー人数が少ない、AWS低コスト制約、Aurora/Lambda構成、認証がモック段階、等）
- [ ] 各リスクに対してどのテスト活動（レイヤー）で軽減するかを対応付ける
- [ ] 完了条件: リスク一覧と対応テスト活動の対応表を作成する

### Phase 3: テストアーキテクチャ設計の方針決定

- [ ] 書籍 Part III の2アプローチ（「優れたテストレベルの責務を拡大する」／「個々の品質確保で全体を支える」）のどちらを基本方針にするか決定する
- [ ] 現状の方針（責務が生まれた場所でのみテストする。`testing.md` に記載済み）が書籍のどちらの方針に近いか整理する
- [ ] 完了条件: 採用する設計アプローチと理由を1段落で書ける状態にする

### Phase 4: リグレッションテスト戦略の決定

- [ ] 現状のリグレッション対応手段（CI上のVitest/Playwright実行、PRレビュー）を確認する
- [ ] 「保護して変更する（Cover & Modify）」「コンポーネント間の結合度を下げる設計」など書籍の対処法から、追加で採用するものがあるか判断する
- [ ] 完了条件: 採用する対処法のリストと、採用しないものの理由を記載する

### Phase 5: シフトレフト/シフトライトの適用範囲決定

- [ ] シフトレフト（Wモデル、ATDD的な受け入れ条件の先行定義）について、既存の ワークフローでどこまで実現できているかを確認する
- [ ] シフトライト（カナリアテスト、カオスエンジニアリング等）を個人開発規模で採用するか判断する（運用サポート体制がないため不採用が濃厚。判断と理由を明記）
- [ ] 完了条件: 各プラクティスの採用・不採用とその理由、見直し条件を記載する

### Phase 6: 自動テスト方針の確認・補強

- [ ] 書籍 Part IV のアンチパターン（銀の弾丸願望、後の祭りの自動化、GIGO、ジリ貧の自動テスト）に現状が当てはまっていないか確認する
- [ ] FIRSTの原則・xUTPの原則と現状のテストコードの整合を確認する
- [ ] 完了条件: 現状維持で良い点／改善が必要な点のリストを作成する

### Phase 7: テスト計画のドキュメンテーション運用方針決定

- [ ] 戦略書の格納先を決定する（新設 `docs/design/non-functional/test-strategy.md` か、既存 `testing.md` への統合か）
- [ ] 書籍 Part V の「テンプレート穴埋め計画」アンチパターンを避けるため、更新頻度・更新トリガー・誰が更新するかを決める
- [ ] 完了条件: 格納先・更新運用ルールが確定する

### Phase 8: 戦略書ドラフト作成・レビュー

- [ ] Phase 1〜7 の決定事項を戦略書としてまとめる
- [ ] ユーザーレビューを受ける
- [ ] 完了条件: レビュー指摘を反映した戦略書が確定する

### Phase 9: 既存ルールへの反映

- [ ] 確定した戦略のうち、常時ルール化すべき内容を `.claude/instructions/testing.md` に反映する
- [ ] `docs/design/non-functional/testing.md` との重複・矛盾がないか確認する
- [ ] 完了条件: 反映漏れがない状態で両ドキュメントの役割分担が明確になっている
