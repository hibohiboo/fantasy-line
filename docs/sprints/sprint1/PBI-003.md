## 引継ぎ情報（2026-05-10 セッション — ID 型の検討）

### 経緯

Phase 2（DB スキーマ追加）の着手前に、`residents.id` の型について BIGINT vs UUID の比較検討を行った。

### 比較で確認した観点

| 観点 | BIGINT（serial） | UUID v7 |
|---|---|---|
| ストレージ | 8 バイト | 16〜36 バイト |
| INSERT 性能 | ◎ 連番で断片化なし | ○ v7 は時刻順で断片化少 |
| ID 推測リスク | △ 総件数・作成順が透けて見える | ◎ 推測不可 |
| villages との一貫性 | ◎ 同じ型 | △ 型が混在 |

### 当初の判断（BIGINT を選択）

- 権限チェック（`owner_id` 照合）で ID 推測攻撃は既に防がれている
- `villages` が `serial`（BIGINT）を使っており型を統一できる
- 実装コストが低い

→ **PBI-003 では `serial`（BIGINT AUTO_INCREMENT）のまま進める**と決定。

### 追加の要望で方針変更が発生

その後、将来のマルチテナント構成について以下の方針が示された。

- `villages`・`residents` テーブルはテナントごとに別スキーマへ分離する予定
- スキーマ分離後も複数テナントをまたいだ管理者ビューを設ける
- 連番 ID では「テナント A の id=5」と「テナント B の id=5」が衝突し、操作ミスのリスクがある
- UUID（グローバル一意）であれば ID 単体で安全に扱える

### 結論

- **PBI-003 は引き続き `serial`（BIGINT）で実装する**（既存の `villages` と合わせる）
- ID 体系の変更（`villages.id`・`residents.id` を UUID v7 に移行）は **PBI-016** として切り出した
  - 参照先: [PBI-016](../../pbi/00-infrastructure/PBI-016.md)
  - 優先度: Phase 2（PBI-003 完了後・マルチテナント移行 PBI の前に実施）

export const residents = pgTable('residents', {

## Zod スキーマ（実装起点）

`packages/schema/src/resident.ts` を新規作成する。

```typescript
import { z } from 'zod';

const katakanaRegex = /^[ァ-ヴー]+$/;

export const CreateResidentSchema = z.object({
  name: z.string().min(1).max(128),
  nameKana: z.string().min(1).max(128).regex(katakanaRegex, '読みはカタカナで入力してください'),
  birthDate: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, '生年月日はYYYY-MM-DD形式で入力してください'),
  villageId: z.number().int().positive(),
});

export const ResidentSchema = z.object({
  id: z.number(),
  name: z.string(),
  nameKana: z.string(),
  birthDate: z.string(),
  villageId: z.number(),
  createdAt: z.date(),
});

export const ResidentWithVillageSchema = ResidentSchema.extend({
  villageName: z.string(),
});

export const CreateResidentResponseSchema = z.object({
  resident: ResidentSchema,
});

export const ListResidentsResponseSchema = z.object({
  residents: z.array(ResidentWithVillageSchema),
});

export const ListVillageResidentsResponseSchema = z.object({
  residents: z.array(ResidentSchema),
});

export type CreateResidentInput = z.infer<typeof CreateResidentSchema>;
export type Resident = z.infer<typeof ResidentSchema>;
export type ResidentWithVillage = z.infer<typeof ResidentWithVillageSchema>;
export type CreateResidentResponse = z.infer<typeof CreateResidentResponseSchema>;
export type ListResidentsResponse = z.infer<typeof ListResidentsResponseSchema>;
export type ListVillageResidentsResponse = z.infer<typeof ListVillageResidentsResponseSchema>;
```

## 認証モック方針（PBI-014 実装前）

PBI-014（ログイン機能）が未実装の間は、以下のモック方式で `owner_id` を取得する。

- ローカル/テスト: リクエストヘッダー `X-User-Id` の値を使用する
- 値が存在しない場合は 401 Unauthorized を返す（PBI-001 と同じパターン）

## 権限チェック実装方針

`createResident` および `listVillageResidents` ハンドラーでは、以下の順序で権限チェックを行う。

```typescript
// 1. 村の存在確認と権限チェック
const [village] = await db
  .select()
  .from(villages)
  .where(eq(villages.id, villageId));

if (!village || village.ownerId !== ownerId) {
  return json(403, { error: 'Forbidden' });
}

// 2. 住人の登録（またはクエリ）
```

存在しない村と他ユーザーの村をまとめて 403 で返すことで、村の存在をほかのユーザーに推測させない。

## 全住人一覧のクエリ方針

`listResidents` ハンドラーは、住人と村の JOIN クエリで取得する。

```typescript
const result = await db
  .select({
    id: residents.id,
    name: residents.name,
    nameKana: residents.nameKana,
    birthDate: residents.birthDate,
    villageId: residents.villageId,
    villageName: villages.name,
    createdAt: residents.createdAt,
  })
  .from(residents)
  .innerJoin(villages, eq(residents.villageId, villages.id))
  .where(eq(villages.ownerId, ownerId))
  .orderBy(asc(residents.nameKana));
```

## 暫定設計・制約事項

| 項目 | 内容 |
|---|---|
| `birth_date` の妥当性検証 | DB は `DATE` 型。Drizzle は `mode: 'string'` で "YYYY-MM-DD" 文字列として扱う。形式チェックのみ。無効日付（例: 2000-02-31）・未来日の検証は行わない |
| カタカナの範囲 | 全角カタカナ（`ァ-ヴ`）と長音符（`ー`）のみ許可。半角カタカナは不可 |
| 読みの重複 | 同一村に同じ読みの住人を複数登録できる（ユニーク制約なし） |
| ページネーション | 現時点では実装しない（住人数が増えた段階で PBI を起こして追加する） |
