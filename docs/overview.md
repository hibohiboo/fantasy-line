# fantasy-line サービス全体概要

## ビジョン（Why）

**「人が作る設定」から「世界が生きる体験」へ**

ファンタジー世界の村を、単なるデータの集まりではなく、
**時間とともに振る舞い、観察できる"生きたシミュレーション"**として扱えるようにする。

### 対象ユーザー

| ユーザー | 用途 |
|---|---|
| 作家・ゲーム開発者 | 世界観の整合性チェック |
| TRPGプレイヤー | セッション外でも世界が動き続ける没入感 |
| 個人ユーザー | "眺めて楽しい箱庭" |

---

## プロダクトゴール（What）

### 1. 世界の「一貫性」と「自然さ」を担保する

ユーザーが入力した設定が、矛盾なく動くこと。

- 生活リズム → 職業と整合する（鍛冶屋が昼寝ばかりしない）
- 魔力消費 → 行動と連動する
- 村全体 → 昼夜・季節で変化する

> **ゴール：** 「入力した設定から、違和感のない1日が自動生成される」

### 2. "観察して楽しい"状態を作る

ただのCRUDではなく、観測可能な変化があること。

- 村人ごとの1日ログ生成
- 村全体のヒートマップ（時間 × 活動）
- 魔力消費の時系列グラフ

> **ゴール：** 「村を眺めるだけでストーリーが浮かぶ」

### 3. "ゆらぎ（ばらつき）"を持たせる

リアルさは「完全一致」ではなく「揺れ」で生まれる。

- 起床時間 ±30分の揺らぎ
- 職業ごとの確率的行動
- イベント（雨・祭り・体調不良）

> **ゴール：** 「毎日少し違うが、性格は一貫している」

### 4. 村単位の「運営・管理モデル」

SaaSとしての差別化ポイント。

- 村管理者（Owner）による一元管理
- 複数ユーザーでの共同編集（将来的に）
- 村ごとの設定テンプレート

> **ゴール：** 「1つの世界を複数人で育てられる」

## コアコンセプト

> **このサービスの本質：「状態」ではなく「時間変化」を扱うこと**

| 普通のサービス | このサービス |
|---|---|
| 村人 = データ | 村人 = 時間とともに変化する存在 |

---

## 差別化ポイント

### ① "因果関係がある"

```
行動 → 魔力消費
在宅 → 消費増
夜   → 光源消費増
```

ただのランダムではなく「理由がある」シミュレーション。

### ② "説明できるシミュレーション"

- 「なぜこの人は夜更かししたのか？」
- 「なぜこの家の魔力が増えたのか？」

LLMで説明文を生成することで、観察体験が大幅に向上する。

### ③ "物語生成に繋がる"

- 「この村で起きた1日」を文章化
- NPCのセリフ生成
- ロアグラフ構想との連携

---

## 主要ドメインモデル

```
Village（村）
  └── Resident（住人）
        └── Household（家）
        └── Job（職業）
        └── ScheduleTemplate（生活パターン）

Simulation
  └── DailySimulation（1日生成結果）
        └── ManaUsage（魔力消費ログ）
```

**重要な設計方針：「テンプレート」と「生成結果」を分離する**

- `ScheduleTemplate` ← ユーザーが定義する雛形（再利用・比較可能）
- `DailySimulation` ← テンプレートから生成した1日の記録（イミュータブル）

この分離により、再現性・比較・差分分析が可能になる。

## MVP ロードマップ

### Phase 1 — 「1日が出る」こと（最優先）

- 村 CRUD
- 住人 CRUD
- 職業マスタ
- シンプルな生活リズム（固定 or 軽いランダム）
- 1日シミュレーション生成（JSON出力）

### Phase 2 — 「観察できる」こと

- 魔力消費モデルの導入
- 時系列グラフ可視化
- ばらつき（ゆらぎ）導入

### Phase 3 — 「物語になる」こと

- イベントシステム（雨・祭り・体調不良）
- ストーリー文章生成（LLM連携）
- NPCセリフ生成

## 技術スタック

### アーキテクチャ概要

```
Browser (Vue 3)
    │
    ▼
API Gateway
    │
    ▼
Lambda (Node.js) ── Drizzle ORM ── Aurora MySQL (AWS RDS)
```

### スタック詳細

| 層 | 技術 |
|---|---|
| フロントエンド | Vue 3 + Vite + Pinia + Vue Router |
| バックエンド API | Node.js (Lambda) |
| スキーマ共有 | Zod（`packages/schema`） |
| ORM | Drizzle ORM |
| データベース | Aurora MySQL（本番） / Docker MySQL（ローカル） |
| インフラ | AWS CDK |
| Lint / 型チェック | ESLint + TypeScript（`packages/eslint-config`, `packages/typescript-config`） |
| パッケージ管理 | npm workspaces（monorepo） |

### ディレクトリ構成

```
fantasy-line/
├── apps/
│   ├── api/          # Lambda ハンドラー・DB アクセス層
│   └── frontend/     # Vue 3 フロントエンド
├── packages/
│   ├── schema/           # Zod スキーマ（API/フロント共有）
│   ├── eslint-config/    # ESLint 共通設定
│   └── typescript-config/# TypeScript 共通設定
├── infra/            # AWS CDK インフラ定義
└── docker/           # ローカル開発用 Docker（MySQL）
```

## 開発方針

- **スキーマ駆動：** `packages/schema` の Zod スキーマを Single Source of Truth とし、API・フロントエンド双方で型を共有する
- **テンプレートと結果の分離：** シミュレーションの再現性・比較のため、入力テンプレートと生成結果は常に別テーブルに保持する
- **因果関係の明示：** ランダム性を導入するときは必ず「なぜそうなったか」を記録・説明できる設計にする
- **段階的拡張：** Phase 1 の完了なしに Phase 2 に進まない。各フェーズの完了基準を明確に定める
