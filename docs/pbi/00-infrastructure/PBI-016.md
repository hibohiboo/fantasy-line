# PBI-016 villages・residents の ID を UUID v7 に移行する

## ユーザーストーリー
As a システム管理者
I want villages と residents の主キーを UUID v7 に変更したい
So that スキーマ分離型マルチテナント構成においてクロステナント管理を行う際に、ID 単体でグローバルに一意であることを保証し、テナントをまたいだ操作ミスのリスクをなくせる

## 背景 / 目的
将来的に villages・residents テーブルをテナント（村オーナー）ごとに別スキーマへ分離する構成を検討している。
スキーマ分離後も複数テナントをまたいだ管理者ビューを設ける場合、連番 ID（BIGINT AUTO_INCREMENT）では「テナント A の id=5」と「テナント B の id=5」が衝突し、常に「テナント + id」の2値を管理しなければならない認知負荷と操作ミスのリスクが生じる。
UUID v7（時刻順）を採用することで、ID 単体でのグローバル一意性を確保しつつ、連番に近い挿入順序を保ち MySQL のクラスタインデックス断片化を抑制する。

## スコープ
- 含む
  - `villages.id` の型を `serial`（BIGINT）から `varchar(36)`（UUID v7）に変更
  - `residents.id` の型を `serial`（BIGINT）から `varchar(36)`（UUID v7）に変更
  - `residents.village_id` の型を `bigint` から `varchar(36)` に変更（villages.id 参照のため）
  - Drizzle ORM スキーマの更新（`apps/api/src/db/schema.ts`）
  - マイグレーションの作成・適用
  - 各ハンドラー（createVillage・listVillages・createResident・listResidents・listVillageResidents）の ID 生成ロジック追加
  - 共有スキーマ（`packages/schema`）の型更新（`id: z.string().uuid()`）
  - フロントエンド（Pinia ストア・コンポーネント）の型更新
  - 影響を受ける全テストの更新
- 含まない
  - 本番 DB の既存データマイグレーション（新規テーブルのみが対象のため不要）
  - UUID v7 以外のバリアント（v4・ULID など）への変更
  - `binary(16)` 形式への変更（varchar(36) で実装する）

## ユースケース
### メイン
1. 村を新規作成すると UUID v7 が id として払い出される
2. 住人を新規登録すると UUID v7 が id として払い出される
3. 管理者がクロステナント管理画面で住人 ID を扱う際、テナントをまたいでも ID が一意であることが保証される

### 例外
- 不正な形式の UUID が API に送られた場合は 400 を返す（既存バリデーションで対応済み）

## 受け入れ条件（Gherkin）

```gherkin
Scenario 1: 村を作成すると UUID v7 形式の id が返される
  Given 管理者がログインしている
  When 村「エルムの村」を作成する
  Then レスポンスの id が UUID 形式（xxxxxxxx-xxxx-7xxx-xxxx-xxxxxxxxxxxx）である

Scenario 2: 住人を登録すると UUID v7 形式の id が返される
  Given 管理者がログインしており、村「エルムの村」が存在する
  When 住人「タロウ」を登録する
  Then レスポンスの id が UUID 形式である

Scenario 3: 複数テナントで id が衝突しない
  Given テナント A の村に住人が登録されており、テナント B の村にも住人が登録されている
  When 全住人の id を列挙する
  Then すべての id が一意である（重複なし）

Scenario 4: 既存の村・住人 CRUD が引き続き動作する
  Given UUID v7 移行後の DB で動作している
  When 村の作成・一覧取得・住人の登録・一覧取得を実行する
  Then すべて正常に動作する（201/200 が返される）
```

## ルール（Example Mapping）

- Rule 1: id は UUID v7 形式（時刻順）で生成する
  - Example: 村作成 → id が `019f...` 形式の UUID v7 で返される
  - Example: 短時間に複数登録 → id が時刻順に近い順序で並ぶ

- Rule 2: id の生成はアプリケーション層で行う（DB 側の AUTO_INCREMENT に依存しない）
  - Example: ハンドラーで `uuidv7()` を呼び出して INSERT する

- Rule 3: 既存の全 API の入出力スキーマで `id` は `z.string().uuid()` とする
  - Example: `CreateVillageResponseSchema` の `id` が `z.string().uuid()` でパース成功
