# PBI-022 設計ドキュメントから実装詳細を除去し「仕様の合意記録」に再編する

## ユーザーストーリー

As a 開発者
I want 設計ドキュメントを「何を・なぜ作るか」の合意記録として読めるようにしたい
So that ファイル名やコンポーネント名が変わるたびにドキュメントを直す手間がなくなり、仕様の本質が読み取れるようになる

## 背景 / 問題

`.claude/skills/doc-coauthoring/SKILL.md` の基本原則:

> - 設計ドキュメントは「仕様を明らかにした判断と合意の記録」である
> - 「実装の指示書」ではない
> - 実装が React でも Vue でも、ファイル名が変わっても意味を持つ内容だけを書く

現在の `docs/design/detail/` 配下のドキュメントはこの原則に違反しており、
**「何のファイルをどう書くか」という実装指示書**になっている。

### 具体的な違反箇所

**`docs/design/detail/village.md`**

| 違反の種類 | 内容 |
|---|---|
| ファイルパス一覧 | 「実装影響コンポーネント一覧」テーブルにフルパスを列挙 |
| 実装コード | Zod スキーマの TypeScript コードブロック全体 |
| 実装コード | Pinia ストアの関数シグネチャ（`ref<Village[]>()` 等） |
| 実装名のセクション | `### VillageListView.vue`、`### VillageCreateView.vue` という見出し |
| ファイルパス付きセクション見出し | `### Pinia ストア（apps/frontend/src/features/village/villageStore.ts）` |

**`docs/design/detail/resident.md`**

village.md と同じ構造のため同様の違反がある。

**`docs/design/detail/screen/village.md`**

| 違反の種類 | 内容 |
|---|---|
| ORM クエリコード | Drizzle の `.select().from().orderBy()` コードブロック |
| 実装名のセクション | `### 村一覧画面（VillageListView.vue）` という見出し |

**`docs/design/detail/screen/resident.md`**

screen/village.md と同様の違反を含む可能性がある（要確認）。

### 違反が引き起こす問題

- PBI-019（API フォルダ再編）・PBI-020（フロントエンドフォルダ再編）のたびに
  ドキュメントのファイルパス更新が発生した → 本 PBI でも修正が必要だった
- 「なぜその設計にしたか」が読み取れず、コード自体を読むのと変わらない
- 実装技術（Pinia / Zod / Drizzle）が変わったとき、設計書まで全面改訂が必要になる

## スコープ

### 含む

- `docs/design/detail/village.md` の再編
- `docs/design/detail/resident.md` の再編
- `docs/design/detail/screen/village.md` の再編
- `docs/design/detail/screen/resident.md` の確認と必要に応じた再編

### 含まない

- API 仕様（URI・HTTP メソッド・リクエスト/レスポンス形式）の変更 — 外部から見える仕様として残す
- エラーハンドリング方針・バリデーションルール表の変更 — 仕様として適切
- データモデル（ER 図・テーブル定義）の変更 — ドメインモデルとして適切
- `docs/design/style-guide.md` — スタイルガイドは実装指針を扱う文書のため対象外
- ロジックや実装の変更（ドキュメントのみの改訂）

## 変更方針

### 削除するもの（寿命が短い）

- ファイルパスを列挙した「実装影響コンポーネント一覧」テーブル
- TypeScript / Zod / Drizzle のコードブロック
- Pinia ストアの関数シグネチャ
- ファイル名・コンポーネント名を含むセクション見出し（例: `### VillageListView.vue`）

### 残すもの（寿命が長い）

- 画面・URI・API・状態遷移など外部から見える仕様
- バリデーションルール（コードではなく表形式の仕様）
- エラーハンドリング方針
- データフロー・処理フロー（Mermaid シーケンス図）
- 権限・認可の判断基準
- コンポーネント分割の「考え方」（名前ではなく役割の記述）
- テスト観点
- 実装上の注意点（「なぜ」が書かれているもの）

### 変換例

**Before（実装指示書）:**

```markdown
### Pinia ストア（`apps/frontend/src/features/village/villageStore.ts`）

\`\`\`typescript
const villages = ref<Village[]>([])
const isLoading = ref(false)
const error = ref<string | null>(null)

async function fetchVillages(): Promise<void>
async function createVillage(name: string): Promise<Village>
\`\`\`
```

**After（仕様の合意記録）:**

```markdown
### フロントエンドの状態管理

村一覧画面と村作成画面は状態（一覧データ・ローディング・エラー）を共有する。
以下の操作を状態として保持する。

- 自分の村一覧（GET /api/villages の結果）
- ローディング状態（API 呼び出し中）
- エラー状態（最後のリクエストが失敗したか）

ページ遷移しても一覧データを再取得するのではなく、操作後に楽観的更新または再フェッチを行う。
```

## 受け入れ条件（Gherkin）

```gherkin
Scenario 1: ファイルパスが設計書に残っていない
  Given 再編後のドキュメントが存在する
  When ドキュメントを通読する
  Then `apps/frontend/src/` や `apps/api/src/` で始まるファイルパスが登場しない

Scenario 2: 実装コードが設計書に残っていない
  Given 再編後のドキュメントが存在する
  When ドキュメントを通読する
  Then TypeScript / Zod / Drizzle のコードブロックが登場しない
  And API 仕様のリクエスト/レスポンス JSON 例は例外として許容する

Scenario 3: 外部仕様は保持されている
  Given 再編後のドキュメントが存在する
  When ドキュメントを通読する
  Then API の URI・メソッド・ステータスコード・レスポンス形式が読み取れる
  And バリデーションルールが仕様として読み取れる
  And エラーハンドリング方針が読み取れる

Scenario 4: 「なぜ」が読み取れる
  Given 再編後のドキュメントが存在する
  When 設計上の判断（ソート順・権限チェック位置・楽観的更新等）の箇所を読む
  Then その判断の理由が文章として書かれている
```
