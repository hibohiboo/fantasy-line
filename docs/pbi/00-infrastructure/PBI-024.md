# PBI-024 プロジェクトのテスト戦略を策定する

## ユーザーストーリー

As a このプロジェクトの開発者
I want 読書メモ（`docs/notes/software-testing-guide.md`）の知見を反映したテスト戦略を整理したい
So that 各PBI実装時にテストレベル・テストタイプの責務分担、リグレッション対応、自動化方針を毎回ゼロから考えずに判断できる

## 背景 / 目的

- 既存の `.claude/instructions/testing.md` と `docs/design/non-functional/testing.md` は「実装時の具体的なテストルール」（責務分離、レイヤー別責務表、命名規則）を扱っているが、「なぜそのテストレベルを採用するか」「どのリスクに対してどの戦略で備えるか」というテスト戦略レベルの整理がまだない
- 個人開発・低コスト・小規模スプリント運用というこのプロジェクト特有の制約下で、書籍が紹介する戦略（リスクベーステスト、テストアーキテクチャ設計、リグレッション戦略、シフトレフト/シフトライト、Wモデル等）をどこまで・どのように採用するかを明文化したい
- このPBI自体は「戦略書を作るための計画」を立てるところまでをスコープとする（戦略書本体の執筆は計画確定後の後続フェーズで行う）

## スコープ

- 含む
  - `docs/notes/software-testing-guide.md` の反映候補の整理
  - テスト戦略書として最終的に決めるべき論点の洗い出し
  - 論点ごとの調査・意思決定の進め方（計画）を `docs/plan/PBI-024.md` にまとめる
- 含まない
  - テスト戦略書の本文確定（後続フェーズ）
  - `.claude/instructions/testing.md` 等既存ルールの改訂（戦略確定後に反映）
  - 個別PBIのテスト実装

## ユースケース

### メイン

1. 開発者が読書メモを読み、プロジェクトに関係する論点を抽出する
2. 論点ごとに「現状」「書籍の提案」「本プロジェクトでの採用判断が必要な理由」を整理する
3. 論点を解決する順序・進め方を計画として `docs/plan/PBI-024.md` にまとめる
4. 計画に対しレビューを受ける

### 代替

- 論点が多すぎる場合 → MVP優先度に基づいて着手順を絞る

### 例外

- 書籍の提案が個人開発の規模に合わない場合 → 「採用しない」と明記し理由を残す

## 受け入れ条件（Gherkin）

```gherkin
Feature: プロジェクトのテスト戦略を策定するための計画を立てる

  Scenario: 論点が整理されている
    Given 読書メモ docs/notes/software-testing-guide.md が存在する
    When 計画ドキュメントを確認する
    Then プロジェクトに関係する論点（テストレベル/タイプ設計、リスクベースの優先順位、リグレッション戦略、自動化方針、ドキュメント運用）が一覧化されている

  Scenario: 各論点に進め方が定義されている
    Given 計画ドキュメントが存在する
    When 各論点を確認する
    Then 論点ごとに「決めること」「参照する情報」「完了条件」が記載されている

  Scenario: 計画がドキュメントとして保存されている
    Given 計画の検討が完了している
    When docs/plan/PBI-024.md を確認する
    Then 計画が読める状態で保存されている
```

## ルール（Example Mapping）

- Rule 1: 既存の `testing.md`（実装ルール）と新しい戦略整理は役割を分ける
  - Example: 「レイヤー別テスト責務表」は既存 `testing.md` に残し、戦略書では参照するだけにする
- Rule 2: 個人開発・低コストという制約を踏まえ、書籍の提案を無条件に採用しない
  - Example: シフトライトテスト（カナリア・カオスエンジニアリング）は本プロジェクト規模では「採用しない」と明記し、見直し条件を残す

## 不明点 / 質問

- 戦略書の最終的な格納先（`docs/design/non-functional/test-strategy.md` 新設 か、既存 `testing.md` への統合か）は計画策定時（Phase 7）に決める

## INVESTチェック

- Independent: OK（既存実装に依存しないドキュメント整備タスク）
- Negotiable: OK（論点の優先順位・深さは交渉余地あり）
- Valuable: OK（以降のPBIでテスト方針判断のブレを減らせる）
- Estimable: OK（読書メモという確定済み入力があるため見積もり可能）
- Small: OK（計画策定のみに絞っているため1セッションで完了可能）
- Testable: OK（Gherkinシナリオで確認可能）
