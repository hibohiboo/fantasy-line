# PBI-SaaS-001 マルチテナント SaaS 化 — 設計

Sprint: 未割り当て / 作成日: 2026-06-17

---

## ユーザーストーリー

As a サービサー（本サービスの運営者）  
I want マルチテナント構成の設計方針（Cognito・DB・認可・テナント管理）をドキュメントとして確定したい  
So that 個別テナントの安全なデータ分離と、テナント管理者によるユーザー管理を実装の根拠として進められる

---

## 背景 / 目的

現状のシステムは単一ユーザー（`owner_id` によるリソース所有管理）を前提に設計されている。
本 PBI では以下を目的とした設計ドキュメントを作成し、後続の実装 PBI の根拠を整備する。

- **テナント分離**: 異なるテナントのデータが混在しないことを設計レベルで保証する
- **Cognito テナントバインド**: JWT の custom claim にテナント識別子を埋め込み、API がテナントを判別できるようにする
- **スキーマ分離 DB**: コストを抑えつつ Aurora MySQL 上でテナントごとにスキーマ（DB）を分ける
- **テナント管理フロー**: テナント発行はサービサーが行い、テナント内ユーザー管理はテナントシステム管理者が担う

---

## スコープ

### 含む

- Cognito User Pool / App Client 設計（custom claim `tenant_id` の定義）
- テナントプロビジョニングフロー設計（サービサー操作手順・CDK/Lambda での自動化方針）
- スキーマ per テナント設計（Aurora MySQL 上のスキーマ命名規則・接続切替方式・Drizzle ORM 対応）
- テナントユーザー管理フロー設計（テナントシステム管理者によるユーザー招待・削除）
- API 認可レイヤー設計（テナント識別子取得・テナント境界チェックパターン）
- 非機能設計（テナント間の障害波及抑止・ログ分離・コスト影響試算）
- ADR 作成（テナント分離方式・スキーマ per テナント採用理由）
- 既存設計ドキュメント（`security.md`・`api-architecture.md`・`infrastructure.md`）の横断更新

### 含まない

- Cognito User Pool / App Client の実際の CDK 実装
- テナントプロビジョニング Lambda の実装
- スキーマ作成マイグレーションの実装
- フロントエンドのログイン UI 実装
- 課金・プラン管理機能

---

## ユースケース

### メイン

1. サービサーが新テナントを発行する（Cognito グループ作成 + Aurora スキーマ作成 + 初期システム管理者アカウント作成）
2. テナントのシステム管理者がログイン後、テナント内の一般ユーザーを招待・登録する
3. 一般ユーザーがログインし、自テナントのデータのみを参照・操作する
4. API が JWT の `custom:tenant_id` claim を読み取り、該当テナントのスキーマに接続する
5. API がデータ操作時に自テナントスキーマの範囲外へのアクセスを拒否する

### 代替

- テナントシステム管理者が一般ユーザーを削除する（Cognito からも Aurora からも削除）

### 例外

- JWT に `custom:tenant_id` が存在しない場合 → 403 Forbidden（テナント未割り当てエラー）
- 存在しないテナント ID が claim に含まれる場合 → 403 Forbidden（不正テナントエラー）
- テナントスキーマへの DB 接続失敗 → 503 Service Unavailable（テナント管理者・サービサーへ通知）

## ルール（Example Mapping）

- **Rule 1: テナント識別は JWT claim のみで行う**
  - Example: リクエストボディ・クエリパラメータからテナント ID を受け取ってはならない。必ず JWT の `custom:tenant_id` から取得する

- **Rule 2: スキーマ名はテナント ID から一意に導出する**
  - Example: `tenant_id = "acme"` → スキーマ名 `tenant_acme`。スキーマ名の衝突を防ぐため、テナント ID に使用できる文字（英数字・ハイフン・下線等）を定義する

- **Rule 3: テナント内ロールは Cognito グループで管理する**
  - Example: テナント `acme` の管理者は Cognito グループ `acme_admin`、一般ユーザーは `acme_user` のメンバーになる

- **Rule 4: テナント管理者が作成できるのは自テナントのユーザーのみ**
  - Example: テナント `acme` の管理者はグループ `acme_*` 配下へのユーザー追加のみ許可される。`beta_*` グループへの操作は IAM ポリシーで拒否する

- **Rule 5: スキーマ作成はテナントプロビジョニング時に一度だけ行う**
  - Example: テナント発行後のスキーマ変更は、通常の Drizzle マイグレーション（全テナント一括または段階適用）として扱う

- **Rule 6: 既存の `owner_id` 設計との移行方針を明記する**
  - Example: 現在の `owner_id` カラムはテナント分離後も維持し、テナント内のリソース所有者識別に使い続けるか、廃止するかを設計ドキュメントで決定する

- **Rule 7: コスト試算を設計ドキュメントに含める**
  - Example: テナント数 10 / 50 / 100 件を想定した Aurora Serverless V2 ACU 消費・Cognito MAU 費用の概算を記載する

## 不明点 / 質問

- テナント ID の形式: UUID か、意味のある短縮識別子（例: 会社名スラッグ）か？
- `tenant_role` の粒度: `admin` / `user` の 2 種か、複数ロールが必要か？
- テナント管理者が使う「ユーザー管理画面」はこの SaaS に内包するか、Cognito コンソールを直接使わせるか？
- Aurora スキーマ間でマイグレーション（Drizzle `db push` / `migrate`）を一括実行する運用スクリプトの所有者はサービサーか、各テナントか？
- テナント削除（解約）時のスキーマデータ保管期間と削除タイミングの方針は？
- Cognito User Pool は全テナント共用 1 Pool か、テナントごとに別 Pool か？（コスト・管理複雑性の観点）

## INVEST チェック

- **Independent**: OK — 既存の機能実装 PBI（村・住民管理等）と依存関係なし。設計ドキュメントのみの成果物
- **Negotiable**: OK — スキーマ分離方式（per テナント）は確定方針だが、Cognito グループ設計の粒度・管理ツールの有無は交渉余地あり
- **Valuable**: OK — 後続の実装 PBI すべての根拠となる。設計が固まるまで実装を進められない
- **Estimable**: OK — 成果物が「設計ドキュメント群 + ADR 2〜3 件 + 既存ドキュメント横断更新」と明確なため見積もり可能
- **Small**: NG — 設計範囲が広いため、以下への分割を推奨:
  - SaaS-001a: Cognito 設計（claim 定義・グループ構成）
  - SaaS-001b: DB スキーマ per テナント設計（命名規則・接続切替・マイグレーション方針）
  - SaaS-001c: テナントプロビジョニング・ユーザー管理フロー設計
  - SaaS-001d: API 認可パターン設計 + 既存ドキュメント横断更新
  ただし全体像を把握するために一度 PBI として作成し、チームでの分割可否を確認すること
- **Testable**: OK — 各受け入れ条件がドキュメントの存在・記載内容で検証可能
