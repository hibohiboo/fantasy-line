# PBI-014 ログインする

改訂日: 2026-06-18（Amplify UI for Vue 採用・パスワードリセット追加・マルチテナント対応に再改訂）

---

## ユーザーストーリー

As a ユーザー（`servicer_admin` / `servicer_delegate` / `tenant_admin` / `tenant_user`）  
I want Cognito アカウントでログイン・パスワードリセットをしたい  
So that 自分のアクター種別に応じたダッシュボードに安全にアクセスできる

---

## 背景 / 目的

全 PBI の認証前提となる基盤機能。
[auth-cognito.md](../../design/non-functional/auth-cognito.md) で確定した Cognito User Pool（PBI-SaaS-002 で実装）に対し、
`@aws-amplify/ui-vue` の `Authenticator` コンポーネントを使うことで、
サインイン・初回パスワード変更・パスワードリセット・エラーハンドリングを設定のみで実現する。

ログイン後のリダイレクト先は JWT の `custom:user_type` で決定する。
- `tenant_admin` / `tenant_user` → テナントダッシュボード（`custom:tenant_id` で固定テナント）
- `servicer_admin` / `servicer_delegate` → テナント選択画面（複数テナントにアクセスするため）

### 新規ライブラリ採用根拠（`@aws-amplify/ui-vue`）

| 項目 | 内容 |
|---|---|
| 採用理由 | SRP 認証・初回パスワード変更チャレンジ・パスワードリセット・エラーハンドリングを設定のみで実装でき、自前実装より安全でメンテコストが低い |
| 代替案 | `aws-amplify` SDK を直接呼ぶ自前フォーム実装 → チャレンジ対応・エラー分岐を自前で書く必要があり工数とセキュリティリスクが増える |
| 採用しない条件 | breaking change が多発する場合、カスタムデザイン要件が設定範囲を超えた場合 |
| ライセンス | Apache-2.0（AWS 公式） |
| メンテナンス状況 | AWS が公式にメンテナンス中。定期リリースあり |
| セキュリティ | SRP プロトコルを内部実装済み。トークンは Amplify SDK が localStorage で管理（ページリロード対応との trade-off として許容） |
| バンドルサイズ | 木構造シェイキング対応。Authenticator コンポーネントのみ使用 |

## スコープ

### 含む

- `@aws-amplify/ui-vue` の `Authenticator` コンポーネント導入
- サインイン画面（メールアドレス + パスワード入力フォーム）
- サインアップ無効化（`hideSignUp` 設定。アカウント作成は PBI-SaaS-005 の管理 Lambda で実施）
- 日本語ローカライズ（`I18n.putVocabularies` + `I18n.setLanguage('ja')`）
- 初回ログイン時の仮パスワード変更（`NEW_PASSWORD_REQUIRED` チャレンジ: Amplify UI が自動対応）
- パスワードリセット（「パスワードをお忘れですか？」→ 確認コード → 新パスワード設定: Amplify UI が自動対応）
- ログイン後リダイレクト（`custom:user_type` に基づく分岐）
- 未ログイン状態でのアクセス時にログイン画面へリダイレクト（Vue Router ルートガード）
- リフレッシュトークンによるサイレントトークン更新（Amplify SDK が自動処理）
- ログアウト（Cognito グローバルサインアウト + Amplify ストア破棄）
- Pinia store でログイン状態・ユーザー情報（`custom:user_type` / `custom:tenant_id`）を管理

### 含まない

- ユーザー登録・アカウント作成（→ PBI-SaaS-005）
- MFA 設定 UI（ユーザー任意。設定画面は別 PBI）
- ソーシャルログイン（OAuth）
- テナント選択画面の実装（`servicer_*` のログイン後リダイレクト先: 別 PBI。本 PBI では暫定ページでよい）

## ユースケース

### メイン（`tenant_*` ユーザー）

1. ユーザーがログイン画面にアクセスする
2. Amplify UI の Authenticator コンポーネントが表示される（サインアップリンクなし）
3. メールアドレスとパスワードを入力して「サインイン」を実行する
4. Cognito `USER_SRP_AUTH` フローで認証し JWT を取得する
5. Pinia store にユーザー情報（`custom:user_type` / `custom:tenant_id`）を保存する
6. `custom:user_type` が `tenant_admin` または `tenant_user` → テナントダッシュボードへリダイレクト

### メイン（`servicer_*` ユーザー）

1. 同様に認証し JWT を取得する
2. `custom:user_type` が `servicer_admin` または `servicer_delegate` → テナント選択画面（暫定）へリダイレクト

### 代替（初回ログイン・仮パスワード）

1. ユーザーが招待メールの仮パスワードでサインインを試みる
2. Amplify UI が `NEW_PASSWORD_REQUIRED` チャレンジを検出し、自動的にパスワード変更画面を表示する
3. ユーザーが新しいパスワードを設定して送信する
4. 通常ログインフローに戻り、リダイレクトされる

### 代替（パスワードリセット）

1. ユーザーがログイン画面の「パスワードをお忘れですか？」リンクを押す
2. Amplify UI がメールアドレス入力画面を表示し、Cognito から確認コードを送信する
3. ユーザーが確認コードと新しいパスワードを入力して送信する
4. リセット完了後、サインイン画面に戻る

### 代替（トークン期限切れ）

- アクセストークンが期限切れの場合 → Amplify SDK がリフレッシュトークンでサイレント更新し、ユーザーに気づかせない

### 例外

- 認証情報が誤っている場合 → Amplify UI がエラーを表示（日本語ローカライズ済みメッセージ）
- アカウントが無効化されている場合 → エラーメッセージを表示（スタックトレース非表示）
- リフレッシュトークンが期限切れまたは無効な場合 → Pinia store を破棄しログイン画面へリダイレクト
- 未ログイン状態で保護ページにアクセスした場合 → ログイン画面にリダイレクト

## ルール（Example Mapping）

- **Rule 1: Authenticator コンポーネントはサインアップを無効化する**
  - Example: `<Authenticator :hideSignUp="true">` を設定する。アカウント作成は管理 Lambda（PBI-SaaS-005）が行う

- **Rule 2: Amplify SDK のデフォルトトークンストレージ（localStorage）を使用する**
  - Example: Amplify SDK が JWT をローカルストレージで管理する。ページリロード後もセッションを維持できる trade-off として許容する。Pinia store にはユーザー属性（`custom:user_type` / `custom:tenant_id`）のみを保持する

- **Rule 3: 日本語ローカライズを起動時に設定する**
  - Example: `main.ts` で `I18n.putVocabularies(translations); I18n.setLanguage('ja')` を呼び出す。Amplify UI の translations パッケージにない文字列は独自辞書で補完する

- **Rule 4: ログイン後リダイレクト先は `custom:user_type` で決定する**
  - Example: `tenant_*` → テナントダッシュボード。`servicer_*` → テナント選択画面（暫定）。ハードコードせず定数テーブルで管理する

- **Rule 5: 認証エラーの詳細はユーザーに明かさない**
  - Example: Amplify UI のデフォルトエラー表示をそのまま使う。`NotAuthorizedException` のメッセージを独自に差し替える場合も、存在しないユーザーとパスワード誤りを区別しない

- **Rule 6: リフレッシュトークンが無効なら必ずログイン画面に戻す**
  - Example: API 呼び出し時に `AuthTokens` の取得失敗を検出したら Pinia store をクリアして `/login` にリダイレクトする
