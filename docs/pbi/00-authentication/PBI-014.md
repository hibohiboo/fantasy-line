# PBI-014 ログインする

改訂日: 2026-06-18（Cognito SRP 認証・マルチテナント対応に改訂。初版: 旧設計）

---

## ユーザーストーリー

As a ユーザー（`servicer_admin` / `servicer_delegate` / `tenant_admin` / `tenant_user`）  
I want Cognito アカウントでログインしたい  
So that 自分のアクター種別に応じたダッシュボードに安全にアクセスできる

---

## 背景 / 目的

全 PBI の認証前提となる基盤機能。
[auth-cognito.md](../../design/non-functional/auth-cognito.md) で確定した Cognito User Pool（PBI-SaaS-002 で実装）を使い、
JWT（ID トークン・アクセストークン・リフレッシュトークン）でセッションを管理する。

ログイン後のリダイレクト先は JWT の `custom:user_type` で決定する。
- `tenant_admin` / `tenant_user` → テナントダッシュボード（`custom:tenant_id` で固定テナント）
- `servicer_admin` / `servicer_delegate` → テナント選択画面（複数テナントにアクセスするため）

初回ログイン時（仮パスワード）はパスワード変更画面へ誘導する。

---

## スコープ

### 含む

- ログイン画面（メールアドレス + パスワード入力フォーム）
- Cognito `USER_SRP_AUTH` フローによる認証（パスワードをネットワークに流さない）
- JWT（ID トークン・アクセストークン）の Pinia store 管理
- リフレッシュトークンによるサイレントトークン更新（アクセストークン期限切れ時）
- ログイン後リダイレクト（`custom:user_type` に基づく分岐）
- 未ログイン状態でのアクセス時にログイン画面へリダイレクト（Vue Router ルートガード）
- 初回ログイン時の仮パスワード変更画面
- ログアウト（Cognito グローバルサインアウト + ストア破棄）
- エラーメッセージ表示（認証失敗・アカウント無効化）

### 含まない

- ユーザー登録・アカウント作成（`servicer_admin` が管理 Lambda で実施: PBI-SaaS-005）
- パスワードリセット（別 PBI）
- MFA 設定 UI（ユーザー任意。設定画面は別 PBI）
- ソーシャルログイン（OAuth）
- テナント選択画面の実装（`servicer_*` のログイン後リダイレクト先: 別 PBI）

---

## ユースケース

### メイン（`tenant_*` ユーザー）

1. ユーザーがログイン画面にアクセスする
2. メールアドレスとパスワードを入力して「ログイン」を実行する
3. Cognito `USER_SRP_AUTH` フローで認証する
4. ID トークン・アクセストークン・リフレッシュトークンを取得し Pinia store に保存する
5. JWT の `custom:user_type` が `tenant_admin` または `tenant_user` → テナントダッシュボードへリダイレクト

### メイン（`servicer_*` ユーザー）

1. ユーザーがログイン画面にアクセスする
2. 同様に認証し JWT を取得する
3. JWT の `custom:user_type` が `servicer_admin` または `servicer_delegate` → テナント選択画面へリダイレクト（テナント選択画面は本 PBI では空ページでよい）

### 代替（初回ログイン・仮パスワード）

1. ユーザーが招待メールの仮パスワードでログインを試みる
2. Cognito が `NEW_PASSWORD_REQUIRED` チャレンジを返す
3. パスワード変更画面に遷移しユーザーが新しいパスワードを設定する
4. 設定完了後、通常ログインフローに戻る

### 代替（トークン期限切れ）

- アクセストークンが期限切れの場合 → リフレッシュトークンでサイレント更新し、ユーザーに気づかせない

### 例外

- 認証情報が誤っている場合 → 「メールアドレスまたはパスワードが正しくありません」を表示（どちらが間違いかを明かさない）
- アカウントが無効化されている場合 → 「アカウントが無効です。管理者に連絡してください」を表示
- リフレッシュトークンが期限切れまたは無効な場合 → ストアを破棄しログイン画面へリダイレクト
- 未ログイン状態で保護ページにアクセスした場合 → ログイン画面にリダイレクト

## ルール（Example Mapping）

- **Rule 1: パスワードをネットワークに流さない（USER_SRP_AUTH）**
  - Example: Cognito の `USER_SRP_AUTH` フローを使うことで、パスワードは SRP プロトコルで保護される。`USER_PASSWORD_AUTH` は使わない

- **Rule 2: JWT は Pinia store で管理し、localStorage への直接保存を避ける**
  - Example: Pinia store（メモリ）にトークンを保持する。ページリロード対応が必要な場合は sessionStorage を検討するが、XSS リスクを考慮して localStorage は使わない

- **Rule 3: ログイン後リダイレクト先は `custom:user_type` で決定する**
  - Example: `tenant_*` → テナントダッシュボード。`servicer_*` → テナント選択画面。ハードコードせず、定数テーブルで管理する

- **Rule 4: 認証エラーは詳細を明かさない**
  - Example: メール不存在・パスワード誤りを区別せず「メールアドレスまたはパスワードが正しくありません」と一律表示する

- **Rule 5: リフレッシュトークンが無効なら必ずログイン画面に戻す**
  - Example: Cognito がトークン更新失敗を返したら、ストアをクリアして `/login` にリダイレクトする

## INVEST チェック

- **Independent**: NG — PBI-SaaS-002（Cognito CDK）完了後に着手。その他の PBI とは独立
- **Negotiable**: OK — トークンストレージ戦略（Pinia store / sessionStorage）は交渉余地あり
- **Valuable**: OK — 全 PBI の前提となる認証基盤。これなしに所有者制御が成立しない
- **Estimable**: OK — Cognito SRP 認証 + Vue Router ルートガードで工数見積もり可能
- **Small**: OK — ログイン画面 + ルートガード + トークン管理（テナント選択画面は含まない）
- **Testable**: OK — Gherkin シナリオ + Playwright E2E テストで検証可能
