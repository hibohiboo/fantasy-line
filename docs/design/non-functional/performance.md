# パフォーマンス要件

## 対象読者

開発者・レビュアー。DB設計・API設計・インフラ設計でスケール要件の判断が必要な場合に参照すること。

---

## 現在のスケール前提

| 項目 | 現在の想定値 | 見直しの目安 |
|---|---|---|
| 同時利用ユーザー数 | 10人以下 | 50人を超えたとき |
| villages テーブルの行数 | 数十行程度 | 10,000行を超えたとき |
| API リクエスト頻度 | 低頻度（手動操作のみ） | 自動化・バッチ処理を導入したとき |

この前提が変わった場合は、以下の「保留中の最適化」を順次適用すること。

---

## レスポンスタイム目標

| エンドポイント | 目標値 | 備考 |
|---|---|---|
| POST /villages | 1,000ms 以内 | Aurora Serverless の cold start を含む |
| GET /villages | 500ms 以内 | 同上 |

Aurora Serverless V2 はスケールダウン後の初回リクエストで cold start が発生する。
開発初期はこれを許容し、常時稼働が必要になった時点でインフラ設定を見直す。

---

## 保留中の最適化

スケール前提が変わるまで実装しない。変更時は対象 PBI で実施する。

| 最適化内容 | 対象テーブル/機能 | 適用条件 |
|---|---|---|
| `villages.owner_id` にインデックスを追加 | villages | ユーザー数が50人超、または village 行数が10,000行超 |
| GET /villages にページネーションを追加 | villages 一覧 | 1ユーザーあたりの village 数が100件超 |

---

## 現時点での方針

- インデックスは必要になってから追加する（早期追加は書き込みオーバーヘッドと管理コストの無駄）
- ページネーションは不要。全件返却で問題ない
- N+1 クエリは発生する構造を作らない（ループ内 SELECT 禁止）
- キャッシュ戦略は不要（データ量・頻度ともに閾値以下）
