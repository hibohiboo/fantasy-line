# 基本設計 — 住人管理（resident）

## 目的と背景

fantasy-line のシミュレーションは「村の住人」を構成員として成立する。
村（PBI-001）が作成できるようになった次のステップとして、村の構成員である住人を登録・一覧表示できる必要がある。

住人の生年月日はシミュレーション（PBI-007）で年齢ごとのライフサイクル（労働力・消費など）を算出する目安として使用する。
PBI-003 では名前・読み・生年月日・所属村IDという最小限の情報のみで登録できるようにする。詳細情報（職業・性格タグなど）は PBI-004 で拡充する。

## 対象読者

- プロダクトオーナー（受け入れ条件の確認）
- 開発者（実装方針の把握）
- レビュアー（設計妥当性の確認）

## 機能概要

| 機能 | 説明 |
|---|---|
| 住人の登録 | 管理者が名前・読み（カタカナ）・生年月日・所属村を指定して住人を登録する |
| 住人一覧表示（全体） | ログイン中のユーザーが管理するすべての村の住人を読み昇順で一覧表示する（所属村の列あり） |
| 住人一覧表示（村別） | 指定した村に所属する住人のみを読み昇順で一覧表示する（所属村の列なし） |
| 権限制御 | 自分の村にのみ住人を登録できる。認証済みユーザーのみAPIアクセス可能 |

**スコープ外（将来PBI）:**
- 職業・性格タグの設定 → PBI-004
- 住人の削除・編集 → PBI-015
- ページネーション → 性能要件確定後
- 生年月日を使った年齢計算・シミュレーション反映 → PBI-007

## システム構成

```
Browser (Vue 3 + Pinia + Vue Router)
    │  POST /api/residents
    │  GET  /api/residents
    │  GET  /api/villages/:id/residents
    ▼
API Gateway
    │
    ▼
Lambda (Node.js)
  ├── createResident handler    … バリデーション → DB 書き込み
  ├── listResidents  handler    … 認証ユーザーIDでフィルタ（全体一覧）
  └── listVillageResidents handler … 指定村IDで絞り込み（村別一覧）
    │
    ▼
Drizzle ORM ── Aurora PostgreSQL (AWS Aurora)
  ├── residents テーブル（新規）
  └── villages テーブル（既存・外部キー参照）
```

実装レベルの影響コンポーネント一覧は [詳細設計](../detail/resident.md) の冒頭を参照すること。

## 主要なユースケースフロー

### メインフロー — 住人を登録する

1. 管理者が住人管理ページ（`/residents`）を開く
2. 「住人を追加」ボタンを押し、住人登録フォームに遷移する
3. 名前・読み（カタカナ）・生年月日を入力し、所属村をドロップダウンから選択する
4. 「登録」ボタンを押す
5. フロントエンドがバリデーションを実行する
6. `POST /api/residents` にリクエストを送信する
7. API がバリデーション・権限チェックを実行し、住人を DB に保存する
8. 住人一覧画面に戻り、登録した住人が読み昇順で表示される

### サブフロー — 村別住人一覧を表示する

1. 管理者が村詳細ページなどから村別住人一覧（`/villages/:id/residents`）を開く
2. その村に所属する住人のみが読み昇順で表示される（所属村の列は不要）

### 代替フロー — 住人が登録されていない場合

- 住人一覧が空の場合は「住人が登録されていません。追加してください」と表示する

### 例外フロー — バリデーションエラー・権限エラー

- 名前が空の場合: フロントエンドでエラーを表示し、リクエストを送信しない
- 読みがカタカナ以外の場合: フロントエンドでエラーを表示し、リクエストを送信しない
- 生年月日が未入力の場合: フロントエンドでエラーを表示し、リクエストを送信しない
- 他ユーザーの村に登録しようとした場合: `403 Forbidden` を返す
- 未ログイン状態でAPIアクセス: `401 Unauthorized` を返す

## データモデル概要

テーブル定義・ER図・CRUD表は [データモデル](../data-model/resident.md) を参照すること。

**概要:**

- `residents` テーブルが中心エンティティ。`village_id` によって `villages` テーブルと N:1 で関連付けられる
- 同一村に同名の住人を複数登録できる（ユニーク制約なし）
- 住人一覧のソートは読み（カタカナ）の昇順

## 制約・前提条件

| 項目 | 内容 |
|---|---|
| 先行PBI | PBI-001（村を作成する）— villages テーブルが存在している必要がある |
| 認証 | PBI-014（ログイン機能）が前提。MVP 開発中は認証モックを使用する |
| DB | Aurora PostgreSQL Serverless V2 / ローカル開発は Docker PostgreSQL |
| 認証ユーザーID | API Gateway の authorizer またはリクエストヘッダー経由で取得（認証実装まではモック） |
| 文字種制限 | 読みはカタカナのみ（全角カタカナ、ひらがな・英数字は不可） |
